## Setup tool (packaging/arch/libfprint-sigfm-0078/synaptics0078-setup → /usr/bin)
- Stdlib-only Python, `#!/usr/bin/python3 -I`, imports nothing from the project. This resolves the brief's "A6 helper and root" question: the data generator stays user-side in tools/synaptics0078_data.py, which now prints the next step `sudo synaptics0078-setup install --from <dir>`.
- `install --from DIR [--force] [--dry-run]`:
  - Reads the source with O_NOFOLLOW|O_NONBLOCK and checks fstat and size before reading. It validates the bytes in memory and writes those same bytes.
  - Validation: module.bin is 10500 B with the pinned sha256; program-<12hex>.bin is 18869 B with opcode 0x02.
  - Writes are atomic (O_EXCL temp file, fsync, rename) into /var/lib/fprint/synaptics0078, owned by root, mode 0700 for the directory and 0600 for the files.
  - It refuses symlinks and directories not owned by root. Under sudo, it also refuses a source dir not owned by SUDO_UID.
  - A differing file is replaced only with --force. An identical file with the wrong mode or owner is fixed.
- `status`: read-only; exit 0 only for a valid, correctly owned set.
- Phase B seam: `load_from_dir()` returns a DataSet that feeds check_dataset/make_plan/carry_out. A comment says phase B adds another loader.
- Test hooks: SYNAPTICS0078_SETUP_TEST_ROOT, _TEST_MODULE_SHA256 and _TEST_EUID. Each one is refused when the real euid is 0.

## Omarchy findings (analysis only; nothing modified)
- /usr/share/omarchy/bin/omarchy-hw-fingerprint:
  - Uses sysfs only. Vendor 06cb is in its list, and a device with no kernel driver bound counts as a reader (usbfs is exempted).
  - So it detects our reader whichever library is installed. It installs nothing.
- omarchy-setup-security-fingerprint:
  - If `omarchy-pkg-missing libfprint-git fprintd usbutils`, it runs `sudo pacman -S --needed --noconfirm --ask 4 libfprint-git fprintd usbutils`.
  - Then `sudo fprintd-enroll "$USER"`, which re-enrolls the right index finger, and `fprintd-verify`.
  - On success it edits /etc/pam.d/sudo and polkit-1 (pam_fprintd plus the lid gate) AND writes /etc/pam.d/omarchy-lock-fingerprint, which enables the lock screen.
- What each case does to our package:
  - Today, with stock libfprint, the setup would swap stock for Omarchy's libfprint-git.
  - With our package providing libfprint-git, and fprintd plus usbutils installed: nothing is installed, so our package is KEPT.
  - Without the libfprint-git provide: our package would be SILENTLY replaced (`--ask 4`).
  - After omarchy-remove-security-fingerprint (`omarchy-pkg-drop fprintd libfprint libfprint-git` matches exact names, so ours stays but fprintd goes), the next Setup would install libfprint-git and SILENTLY replace ours.
  - Migration 1785090473 is a no-op: ours provides libfprint.
- Mitigation, phase A: the libfprint-git provide. Do not run Omarchy "Setup Fingerprint" until B3 (it would enable lock-screen fingerprint and re-enroll), and never Remove then Setup. Optional: a post-update hook that warns if `pacman -Q libfprint-sigfm-0078` fails.
- Mitigation, phase C: the omarchy-pkgs package, with the setup script choosing it when 06cb:0078 is present (`pkg-missing`, then install `libfprint-sigfm-0078`). Also ask that the setup's `--ask 4` install be skipped when any package providing libfprint-git is present, which already holds with our provide.

## Autosuspend finding
- The fork's hwdb lists 06cb:0078 (ID_AUTOSUSPEND=1, ID_PERSIST=0); stock does not. Before the package was installed, the sensor showed control=on, delay=2000 ms, persist=0, wakeup disabled.
- systemd's 60-autosuspend.rules applies only on ACTION=="add". So after `pacman -U`, power/control stays "on" until the next reboot or replug, and only then becomes "auto".
- Autosuspend cannot hit while the device is open:
  - libfprint opens the GUsbDevice in fp_device_open and closes it only in fpi_device_close_complete. The synaptics0078 driver also closes it itself after a failed open.
  - libusb holds the usbfs fd for that whole time, and the kernel's usbdev_open takes usb_autoresume_device until release.
  - libusb does not use USBDEVFS_ALLOW_SUSPEND (no "suspend" string in libusb-1.0.so).
- It CAN hit between fprintd sessions, about 2 s after close. Whether suspend wipes the module is unverified. The driver re-checks RomInfo byte 17 at every open and activation and re-uploads, but that path has never run after autosuspend.
- Upstream convention kept. The README carries the check: step 6 (idle for 10 s, then verify) and step 7 (after a reboot, confirm power/control=auto, idle, verify again).
